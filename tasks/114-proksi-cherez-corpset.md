# Миссия 114 — Прокси через корпсеть

> Уровень: `★★★★★` · Тема: туннель поверх HTTP, энкапсуляция

Прокси через корпоративную сеть: спрятаться за чужим щитом, чтобы никто не видел, откуда ты идёшь.
Джез учится быть тенью за чужой спиной.
— Прокси — это зонтик, — CROW выдыхает дым. — В дождь идти удобнее, но зонтик запоминает, кто под
ним стоял.
Джез учится не оставлять мокрых следов.

## Часть 1 — HTTP-клиент-туннель

Сервер-эмулятор: принимает POST на `/tunnel`, тело — один блок
зашифрованных данных (XOR ключом 0x33), возвращает `DATA: <hex>`
(ответ из тела следующего POST-запроса). Протокол примитивный, но
работает.

Клиент-туннель: читает stdin, режет по 64 байта, каждый блок — POST,
собирает ответы. Проверь на своём тексте:

```bash
$ echo "hello from the grid" | ./tunnel
SENT 5 blocks  RECEIVED 5 blocks
MIRROR OK

## Часть 2 — Полный дуплекс

Теперь туннель оборачивает настоящий TCP-поток: клиент соединяется с
`target:port` локально? Нет — наоборот: локальный клиент (твой чат из
045) подключается к туннелю, туннель оборачивает поток в POST-кадры
и шлёт на корпоративный HTTP-прокси, который их разворачивает в
целевую сеть.

Кадры: `0x01` (данные), `0x02` (конец потока). Очередь на обе стороны.

Проверь полный roundtrip эхо-сервера сквозь туннель:

```bash
$ ./chat 127.0.0.1 1700
> ping
[echo] ping
TUNNEL OVER HTTP: OK (12 frames)

## Подсказки

- Заголовок `Content-Type: application/octet-stream`, keep-alive не нужен.
- Кадры переживают редиректы? Нет — игнорируй, сервер прямой.
- Обе стороны реализуют одинаковый формат (это же твой протокол).
